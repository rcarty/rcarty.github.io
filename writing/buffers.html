Sharing simulation buffers across Vulkan, OpenGL, Direct3D 12 and Metal

NeXus simulates particles and fluids on the GPU and has to show them in the viewport of the app it's plugged into. The simulation and the host app don't share a graphics API or even a device. This is how the native viewport renderer I worked on at INSYDIUM gets simulation data on screen without it leaving the GPU. The code is proprietary, so this page describes the approach and the public APIs it uses.

The problem

The easy way is to read the simulation buffers back to the CPU and hand them to the host as ordinary geometry. With millions of particles that's a big download and a big upload every frame, and the viewport stalls while both happen. The data's already sitting in GPU memory. The job is to let a second API see it.

The simulation runs on Vulkan, or on Metal on a Mac. The host's viewport might be Vulkan, OpenGL, Direct3D 12 or Metal, depending on the app, the platform and the user's settings. Each pairing needs its own way of sharing.

One mechanism per backend

Viewport API How it sees the simulation buffer Copies
Vulkan External memory, exported by one device and imported by the other None
OpenGL A memory object created from the same exported handle None
Metal The same buffer object None
Direct3D 12 A mirror buffer on the GPU, kept in step with a shared fence One, GPU to GPU

Vulkan to Vulkan

The simulation allocates its buffers as exportable memory using VK_KHR_external_memory and gets an OS handle for each allocation. That's a file descriptor on Linux and a Win32 handle on Windows, and on a Mac it's the Metal buffer itself. The renderer imports that handle on the host's device and binds a buffer to it. Both devices now address the same memory, and the renderer reads particle positions straight out of the simulation's storage. The simulation had to handle all three platforms properly, so the same buffers could be passed to whichever API the host was drawing with.

OpenGL

OpenGL can do the same through GL_EXT_memory_object. The renderer creates a memory object, imports the handle Vulkan exported, and creates a buffer backed by it with glNamedBufferStorageMemEXT. From then on it's an ordinary GL buffer that happens to hold live simulation data.

Metal

On a Mac the simulation runs on Metal too, on the same device as the host. The renderer is handed the same buffer object the simulation writes to. This is the easy one.

Direct3D 12

Direct3D 12 can't open the memory handles Vulkan exports, so it can't see the simulation's buffers directly. It gets a mirror, a second buffer that both APIs can open. The simulation copies into the mirror on the GPU, and a fence shared between the two APIs tells Direct3D when that copy has landed.

It isn't zero-copy. The copy never leaves the GPU though, which is what matters for frame time. Direct3D creates the mirror and shares it with Vulkan, because the sharing only works in that direction.

Drawing into the host's own targets

The renderer doesn't draw to its own image and composite it afterwards. Its output goes straight into the host's colour and depth targets, so simulation data sorts correctly against the rest of the scene and picks up the host's own post-processing.

Some hosts don't expose their device or their render pass to plug-ins. For those, the library intercepts the graphics API inside the process. The plug-in issues a marker draw at the point in the frame where the simulation should appear, and the library records its own passes when it sees that marker go by.

The marker is the easy part. The plug-in draws something with a value the host would never produce by itself, like a colour of 10 where the valid range stops at 1. That's easy to spot, easy to intercept, and it marks exactly where our draws go.

The harder part was everything else the host draws. An app like Blender doesn't draw its scene just once. It also writes depth, outlines and other buffers of its own, and our intercepted draw would land in those passes the wrong way. That often showed up as a crash when you clicked in the viewport, usually down to the host's ray-cast picking. The fix was to draw into those depth and extra buffers the way the host expected. RenderDoc was a big help here. It showed what each pass was, what it expected, and how ours could slot in without the host noticing.

Testing four backends at once

A bug in one backend is easy to miss when you only ever look at one. The standalone Dear ImGui app runs one simulation and shows it in side-by-side windows on different backends. If Vulkan and OpenGL disagree, you see it straight away.
