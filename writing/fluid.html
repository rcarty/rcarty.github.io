How the fluid at the top of this page works

The header of this site is a live fluid simulation. It's about 73,000 particles on a desktop, or 23,000 on a phone, simulated and drawn every frame in WebGPU with no third-party libraries. It has two halves. A solver moves the particles, and a renderer turns them into something that looks like one body of liquid. The copy below runs the same code, and the buttons show the images the renderer builds on the way to the final one.

The solver

The fluid is simulated with MLS-MPM, a material point method. Particles carry the mass and velocity. A grid is used as scratch space each step to work out how the particles push on each other, and is cleared before the next one. One step is four compute dispatches.

  • Scatter each particle's mass and momentum to the grid cells around it.
  • Read the density back at each particle, turn it into pressure, and scatter that to the grid as momentum.
  • Divide momentum by mass to get a velocity per cell, add gravity, and stop flow through the walls.
  • Gather the grid velocity back to each particle and move it.

Each particle touches the 27 cells around it, weighted by a quadratic B-spline. It also carries a 3×3 matrix C that describes how velocity varies around it. This is the APIC transfer, and it keeps the rotation and shear that a plain weighted average would smear away. Without it the fluid looks like syrup and goes still far too quickly.

Scattering without locks

The scatter passes have thousands of particles adding to the same grid cell at once, so the adds have to be atomic. WGSL only has atomics for integers, so I multiply mass and momentum by a million, add them as fixed-point i32 values, and let the grid pass divide the scale back out. 

let m = wt * MASS;
let mv = m * (p.v + p.C * dist);
atomicAdd(&cells[idx].m, i32(m * FP));
atomicAdd(&cells[idx].vx, i32(mv.x * FP));
atomicAdd(&cells[idx].vy, i32(mv.y * FP));
atomicAdd(&cells[idx].vz, i32(mv.z * FP));

The catch is range. A cell's momentum has to stay below about 2,147 in solver units before the integer overflows, and this scene doesn't get anywhere near that. Integer adds also give the same total in any order, which float adds don't.

Pressure

The fluid is weakly compressible. Density at a particle comes from the grid mass around it, and pressure comes from how far that is above the rest density. 

let volume = MASS / max(density, 1e-4);
let pressure = max(0.0, u.stiffness * (pow(density / u.restDensity, 5.0) - 1.0));
var stress = mat3x3f(-pressure, 0.0, 0.0, 0.0, -pressure, 0.0, 0.0, 0.0, -pressure);
stress += (p.C + transpose(p.C)) * u.viscosity;

The fifth power makes the fluid push back hard once it's compressed a little, so it holds its volume without needing a pressure solve. The max stops it pulling itself together when density drops below rest, which otherwise shows up as particles clumping at the surface. The last line adds a small viscosity from the velocity gradient that C already holds.

Staying stable at 120 steps a second

The solver runs 120 steps a second. That's only two per frame on a 60 Hz display, which isn't a lot to work with. Three things keep it stable.

  • Particle speed is capped so nothing moves more than 0.8 of a cell in one step. A particle that jumps past the cells it scattered to is how these solvers blow up.
  • Walls are soft. Each particle looks three steps ahead, and if it would end up inside a wall it gets pushed back in proportion. The grid also zeroes the velocity component across each wall in its outer two cells.
  • Pressure is clamped at zero, as above.

Gravity tilts about five degrees each way on a slow sine, so the surface never comes to rest. That stops if the browser asks for reduced motion.

From particles to a surface

Drawing 73,000 spheres looks like frogspawn. Screen-space fluid rendering draws the spheres into offscreen images and then filters those images until they read as one surface. Nothing is meshed, and the cost depends on the number of pixels more than the number of particles.

Each particle is drawn as a square facing the camera. The fragment shader throws away pixels outside the circle and works out how far the sphere's front surface is from the camera at each pixel that's left. 

let r2 = dot(i.uv, i.uv);
if (r2 > 1.0) {
  discard;
}
let p = i.vp + vec3f(i.uv * r.radius, sqrt(1.0 - r2) * r.radius);
o.d = -p.z;

That goes into a float target holding view-space depth. The Depth button shows it. A second pass draws the same squares with additive blending into a thickness target, which ends up holding how much fluid each pixel looks through.

Smoothing the depth

The depth image still has every sphere in it, which the Raw normals button makes obvious. A plain blur would fix that, but it'd also smear the fluid's outline into the background. A bilateral filter avoids the smearing by ignoring samples at a different depth, but it ignores them on a surface seen at a shallow angle too, and that leaves streaks. So I went with a narrow-range filter. It takes samples in pairs, one each side of the pixel. 

if (a < lo || b < lo) {
  continue;
}
if (a > hi) {
  a = d0 + r.radius;
} else {
  lo = min(lo, a - delta);
  hi = max(hi, a + delta);
}

If either sample is in front of the pixel, the pair is dropped, so nearer fluid doesn't bleed in. A sample too far behind, the background included, counts as sitting just behind, which rounds the outline off. Every sample that's accepted widens the range, so the filter follows a sloping surface outwards.

The kernel radius follows the particle's size on screen, so fluid near the camera gets a wide blur and distant fluid a narrow one, up to 24 pixels. It runs horizontally then vertically, twice. The filter isn't truly separable, so this is a bit of a cheat, and the second round hides most of the difference. Thickness gets an ordinary Gaussian blur.

Normals and shading

The last pass rebuilds a view-space position for each pixel and its neighbours from the smoothed depth, and takes the normal from their differences. At the fluid's edge one neighbour is background, so it uses whichever side has the smaller depth step. Otherwise edge normals lean toward the background and the outline goes dark.

The shading is four terms.

  • A body colour from Beer-Lambert absorption. Thin fluid is the accent blue and thick fluid goes dark.
  • A reflection of a simple sky gradient, mixed in by a Schlick Fresnel term so it shows at glancing angles.
  • A tight specular highlight.
  • A faint rim in the accent colour.

Opacity comes from thickness as well, so spray is translucent and the body is solid. The canvas uses premultiplied alpha, which is why the page shows through where there's no fluid.

The cursor

The cursor becomes a ray from the camera. Particles within seven cells of that ray pick up some of the cursor's motion, fading with distance from the ray. It's applied in the gather pass, where each particle is already being updated, so it's close to free.

What it costs

At 60 Hz a frame is eight compute dispatches and nine render passes. Two draw the particles, four smooth the depth, two blur the thickness and one shades. The canvas renders at the display's pixel ratio, capped at 1.5. The loop stops when the header scrolls off screen, and it skips a frame whenever the GPU still has more than one queued, so a slow device drops frames without building a backlog.

On my desktop, an RTX 2080 Ti at 1920×1080 with the full 73,000 particles, the GPU finishes a frame about 7 ms after it's submitted. That leaves plenty of room at 60 Hz. I haven't measured a phone yet.

What I'd change

  • Thin sheets on a breaking crest can still streak. Filtering each axis in turn is an approximation of a full 2D filter, and that's where it shows.
  • There's no refraction. The background behind the fluid is a flat colour, so there's nothing to bend yet.
  • The grid is dense. That's fine for a tank, but an open scene would need a sparse one.
