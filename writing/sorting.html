Radix and bitonic sort in WebGPU and CUDA

I wrote two GPU sorts in WGSL compute shaders, a radix sort and a bitonic sort, and ported each one to CUDA with the same structure, so the two APIs could be compared on the same hardware. This page goes through how each sort works and what the numbers look like. The sorting demo runs both in the browser and animates each pass.

Prefix sum comes first

A radix sort is mostly counting. Each pass counts how many keys have each digit, and a prefix sum over those counts says where every digit's block starts in the output. So the scan is the piece everything else stands on.

Mine works in blocks of 256, one block per workgroup. Each block is scanned in workgroup memory with a Hillis-Steele scan, which takes eight steps for 256 values. The block totals are written to a second, smaller buffer and scanned the same way, and a final sweep adds each block's offset back down. Three levels cover 16 million values.

Radix sort

The sort takes four bits per pass, so 32-bit keys need eight passes. Keys are split into tiles of 1,024, with one 256-thread workgroup per tile. A pass is three stages.

  • Count the 16 digit values in each tile.
  • Prefix sum over all the counts, laid out digit by digit so one scan does the job.
  • Scatter each key to its digit's offset plus its rank among equal digits in the tile.

Ranking is the fiddly bit. A radix sort has to be stable, so two keys with the same digit need to keep their order, which means I can't just hand out slots with an atomic counter.

Ranking inside a tile

Each thread turns its key into a one-hot counter, a 1 in the slot for its digit and zeros elsewhere. A scan over the workgroup then gives every thread the number of earlier keys with the same digit. Sixteen counters would mean sixteen scans, so I pack them. A tile round holds 256 keys, a count fits in 16 bits, and two counters share each 32-bit lane. 

d = (key >> p.shift) & 15u;
let bit = 1u << (16u * (d & 1u));
let lane = d >> 1u;
if (lane < 4u) { a[lane] = bit; } else { b[lane - 4u] = bit; }

That's eight lanes in two vec4u values, and one scan ranks all sixteen digits at once. No atomics touch the output, so the result is the same every run.

Bitonic sort

Bitonic sort is a sorting network. The sequence of compare-and-swap steps is fixed and doesn't depend on the data, which suits a GPU nicely. It does more work than radix, on the order of n log² n compares, but every step is the same simple shape.

Steps whose partners are within 512 keys of each other run inside a tile in workgroup memory, many steps per dispatch. Longer strides read and write global memory, one dispatch per step. At a million keys that's 78 dispatches. The key count has to be a power of two.

The CUDA port

The CUDA kernels are straight ports. Tile sizes, digit width and scan structure are all the same, with __syncthreads() where WGSL has workgroupBarrier(). Warp intrinsics would make the CUDA version faster, and I left them out on purpose so the comparison is between APIs and not between algorithms. CUB's radix sort and scan run alongside as the tuned baseline.

What the numbers say

On an NVIDIA RTX 2080 Ti, sorting 16.7 million random 32-bit keys takes 16.4 ms with the radix sort and 30.6 ms with bitonic. That is 1,023 and 548 million keys a second. The browser's own TypedArray.sort takes 564 ms on the same keys. The prefix sum over the same 16.7 million values takes 0.65 ms. Times are GPU timestamp queries, and submit-to-completion wall clock agrees to within a few milliseconds. The radix sort needs a few runs to settle. The first one or two after the page loads come in anywhere from 22 to 50 ms, and these are the settled figures.

At one million keys the order flips. Radix takes 1.14 ms and bitonic 0.80 ms, against 30 ms for TypedArray.sort, and the prefix sum takes 0.05 ms. That's on the same card, in Chrome 158. A sort this small doesn't keep the GPU busy, and once it clocks down the same sorts take about two and a half times as long, so these are the figures at full speed.

The CUDA port matches the WebGPU version almost exactly at both sizes. It takes 16.3 ms for radix and 30.0 ms for bitonic at 16.7 million keys, and 1.13 ms and 0.71 ms at one million. CUB's radix sort does the 16.7 million in 1.66 ms, about ten times faster than my port. That's expected. Mine is a like-for-like port and CUB is a tuned library.

Bitonic is closer to radix than its extra work would suggest, and at smaller key counts it actually wins. Two things explain that.

  • The radix sort's ranking step costs about 64 barriers per tile per pass. That's four rounds of 256 keys, each with an eight-step scan and two barriers a step. Over eight passes it dominates the sort.
  • Bitonic's steps have no scan in them at all, only compares and swaps in a fixed pattern. Its work grows faster than radix's, so it falls behind as the key count grows.

What's next

  • Eight-bit digits with 4,096-key tiles. That halves the passes for the radix sort.
  • Cheaper ranking. Each thread counts its own keys in turn and the workgroup does one scan, using subgroup operations where the browser has them.
  • The same benchmark at one and sixteen million keys on AMD and Apple GPUs.
